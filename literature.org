* Literate Development
The purpose of this document is to conduct the re-write of the Jetpacs Proof of Concept while also helping me practice a literate development workflow. Ideally, I would really love for this project to serve as a blueprint for what modern application development could look like. Particularly the process of moving from an LLM Generated proof of concept to production. The purpose of literate development is to ensure that I myself, a beginner, fully understand the codebase and every single decision. It is
intended to be a chronological/procedural log of my architectural and implementation decisions in plain English for any Layman to follow and understand. If I, as a layman/beginner can write it, then you should be able to understand it.

** Mission

** Foundation

At its soul, Jetpacs aspires to be nothing more than yet another implementation
of the ever elusive Lisp Machine. Specifically, Jetpacs sets its sights on being
optimized for mobile form factors and touchscreen interaction models. Instead of
rebuilding a Lisp Interpreter from scratch, Jetpacs positions itself to leverage
the existing Lisp Machine experience already ported for Android: Emacs.

At its core, Jetpacs is an Android-focused Companion implementation of the Emacs
Bridge Protocol, a bi-directional implementation of JSON-RPC that
can be transported to any Companion (not just Jetpacs) that can hold a socket
and draw pixels to a canvas. Jetpacs stands atop the EBP to extend the
mobile-native half of the equation to Emacs without either side regressing to
approximations. The EBP wires a formally-specified structured-input that is
interpreted by the Companion who holds no application logic; Emacs computes the
declarations of what to draw, the Companion faithfully renders, caches snapshots
and queues your inputs. By design, Emacs is the source of truth and Elisp
remains the only whole programming language in the system.

This path has been trodden and had its routes carved over decades:
server.el/emacsclient in the 1980s, TCP serving in Emacs 22, =elnode= and
=simple-httpd= in the early-2010s.  This "Emacs-as-a-server" battle-testing
carried the foundational presumption right over to
"smartphone-as-a-client". However, here Emacs promptly hits a wall: even after
constructing infrastructure for NAT traversal and weathering latency, it finds
that it needs a persistent connection or polling from a wireless, intermittent
device whose Operating System is optimized for battery life by aggressively
killing background processes. Emacs diligently listens for a remote dialer who
has been rendered mute by an outright hostile host. Then, in 2009, Richard
Moreland recognized that the state must live on the phone and that a local state
would require a native parser which led to implementing MobileOrg and this
approach was ratified by the core Org Mode with the introduction of
=org-mobile.el=. This Emacs-approximation has been the only rational
implementation: eliminate the link entirely, sync the files, parse them, and
approximate the logic with lossy, destructive round-trips. This approach was
carried through Orgzly, organice, Orgro, beorg, each one shouldering the
Herculean task of reimplementing the file format per platform per question Emacs
had already answered.

Recently, with the advent of Po Lu's diligent Android port released in Emacs 30,
this duplicated org-parsing and application logic can be returned to its home in
Elisp where its introspection and configuration is restored. However, we
promptly find ourselves presented with a program built before graphical
interaction was a baseline and demand it render interactive buttons,
high-refresh animations, create home screen widgets, interop with vCal, access a
hardware camera. Even if the user doesn't care for such niceties, it is only a
matter of time before the Lisp Machine in their hand emboldens them to ask
questions like: "If the phone knows my location, how do I get location
based-reminders?", "Why can't I input using the hardware camera as a barcode
scanner?", or "What if I could execute elisp by scanning an NFC Tag/QR
Code?". We have successfully mobilized our Lisp Machine experience into the
modern world only to find that it requires lugging around an external keyboard
or installing a litany of third-party keyboards that lack sufficient FST
algorithms, workable auto-complete, or spell-check all just to use an
interaction model not built for the form-factor. To implement any such native
functionalities in Emacs is tantamount to open-heart surgery: rewrite the
display engine for animation, bind Android's camera APIs into the C core, write
an elisp software keyboard. In the end, each one of them is an inversion of the
exact approximation mistakes from the Org parsers of the past. Ultimately, Emacs
finds itself a foreign-citizen with no viable path to assimilation.

Contrary to the traditional architecture in =emacs --daemon= where the durable,
long-lived thing listens and the ephemeral client dials, on Android every
process is continually deprioritized specifically so it can be killed for memory
management. For our environment, Jetpacs cannot rely on the traditional
Server-Client approach, therefore, our job is to design for durability when the
only process guaranteed to be alive when you're tapping on the screen is the app
you're looking at. Since we have determined that Emacs should not approximate a
phone, the user's interactions are directed towards the Companion. As the
Companion takes the foreground-app designation it pushes Emacs closer to the
chopping block regardless of what foreground-services it employs per the manual:

#+begin_quote
"Application processes are treated as disposable entities by the system.  When
  all Emacs frames move to the background, Emacs might be terminated by the
  system at any time."
#+end_quote

Further, as soon as the display is off, the Companion itself no longer holds the
foreground-app leaving both processes subject to =Doze= for battery
optimizations. Therefore, the durability must be built into the Companion's disk
cache and the manifest's entry-points. Even though Emacs is the back-end, it is
unable to hold the socket so it is unable to be the listener as shown in AOSP's
own Documentation for Cached Apps Freezer:

#+begin_quote
"App processes in the cached state are frozen 10 seconds after entering the
cached state." (Android 14+)

"If all processes for a particular app are frozen, the system terminates any
active TCP sockets maintained by the app."
#+end_quote

Regardless of what concessions are granted to Emacs in order to keep it running,
the goal post is moved across OS versions, per OEM, per user-setting and has
been proven unstable at best. In an unstable environment where all processes are
ephemeral, the listener cannot also be the back-end. If the back-end is to be
presumed dead and only dials when it is alive, then the listener must cache,
deduplicate, queue the users actions. This internal cache can only be read by
the app that wrote it. Reconstructing the traditional Client-Server interaction
model entails designing the Companion process so that it can die freely, be
revived, rebuilt from disk, make a handshake, then flush the queue. Therefore,
on Android, the Companion, the "client", listens on the socket that Emacs, the
"server", dials into whenever it runs in order to process queued actions and
have state re-derived.

The Lisp Machine experience has been nicely folded into your pocket, but it
remains isolated from interaction in the real world. Emacs has been embodied
with no access to its senses and granted a face whose functions rely upon
non-existent appendages. These are the landmarks of Jetpacs' roadmap.

Ultimately, Jetpacs succeeds when the line between it and Emacs disappears.

#+begin_example
┌─────────────────────────────────┐
│  Jetpacs (Android Companion)    │
│  • Foreground service           │
│  • Renders whatever Emacs sends │
│  • Caches last-known UI state   │
│  • Queues offline actions       │
└──────────────┬──────────────────┘
               │  Emacs Bridge Protocol: JSON-RPC bridge
               │  (loopback socket → signed Unix socket)
┌──────────────┴──────────────────┐
│  Emacs (the source of truth)    │
│  • Pushes native UI specs       │
│  • Handles user action events   │
│  • Runs all the actual logic    │
└─────────────────────────────────┘
#+end_example

** The Envelope
The Roadmap begins with deciding the closed vocabulary, message shape and framing for the what rides the wire.

Three things The Envelope has that plain JSON-RPC doesn't, all portable as conventions on top of JSON-RPC:

Self-describing answers. An ebp reply carries its own kind, so a single logged frame is understandable in isolation. A JSON-RPC response is just {id: 7, result: …} — to know what it means you must find request 7. Small, but real for eyeball-debugging.
Direction annotations. The contract declares who may send each kind (client, companion, both). JSON-RPC has no concept of direction. Keep that table.
Readable string codes. cap-permission beats -32001 for a human. JSON-RPC allows app-defined codes, so you can keep the strings inside error.data.


#+begin_example
closed vocabulary      ebp: methods, payloads, direction rules,
                       handshake, offline queue, node trees
─────────────────────────────────────────────────────
message shape          JSON-RPC 2.0: request/notification/
                       response/error
─────────────────────────────────d────────────────────
framing                Content-Length headers as required
                       by jsonrpc.el
─────────────────────────────────────────────────────
transport              TCP on loopback
#+end_example

*** Gradle Build

**** Dependency and Plugin Resolution

Gradle resolves build plugins separately from libraries used by the
application.

The =pluginManagement= block defines where Gradle searches for plugins
such as Kotlin, Compose Multiplatform, and the Android Gradle Plugin.

The =dependencyResolutionManagement= block defines where project
dependencies are resolved.

#+begin_src kotlin :tangle settings.gradle.kts
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)

    repositories {
        google()
        mavenCentral()
    }
}

rootProject.name = "jetpacs"

include(":shared")
include(":desktopApp")
include(":androidApp")
#+end_src

***** Gradle's project-path separator.
The syntax: =include(":shared")=
means:
#+begin_example
Gradle build
├── :
│   └── root project "jetpacs"
│
└── :shared
    └── subproject
#+end_example
The colon is Gradle's project-path separator.
Later:
: :androidApp
: :desktopApp
will be siblings of =:shared=.

***** Why =FAIL_ON_PROJECT_REPOS=?
Without it, a future module could quietly do this:
#+begin_example
repositories {
    someRandomRepository()
}
#+end_example
and Gradle would start resolving dependencies from somewhere outside the repository policy we established in settings.gradle.kts.

**** Root Plugin Declarations

The root project declares the plugins used by subprojects without
applying those plugins to the root project itself.

This validates plugin resolution and centralizes the plugin versions
while keeping the root project free of Kotlin, Android, or Compose
behavior.

#+begin_src kotlin :tangle build.gradle.kts
plugins {
    alias(libs.plugins.kotlinMultiplatform) apply false
    alias(libs.plugins.kotlinJvm) apply false
    alias(libs.plugins.composeMultiplatform) apply false
    alias(libs.plugins.composeCompiler) apply false
    alias(libs.plugins.androidKmpLibrary) apply false
    alias(libs.plugins.androidApplication) apply false
}
#+end_src

**** Version Catalog

The catalog centralizes versions and coordinates for external Gradle

It does not contain every version-like number in the project. Gradle

**** Shared Kotlin Multiplatform Module

The =shared= project contains Kotlin and Compose UI code intended to be
shared across platform applications.

It currently targets:

- JVM, which will later be consumed by the desktop application.
- Android, using the Android Gradle Plugin's Kotlin Multiplatform
  library target.

The Gradle build itself runs on JDK 25, while Kotlin/JVM output targets
JVM 17 compatibility.

#+begin_src kotlin :tangle shared/build.gradle.kts
import org.jetbrains.kotlin.gradle.dsl.JvmTarget

plugins {
    alias(libs.plugins.kotlinMultiplatform)
    alias(libs.plugins.composeMultiplatform)
    alias(libs.plugins.composeCompiler)
    alias(libs.plugins.androidKmpLibrary)
}

kotlin {
    jvm {
        compilerOptions {
            jvmTarget.set(JvmTarget.JVM_17)
        }
    }

    android {
        namespace = "jetpacs.shared"
        compileSdk = 37
        minSdk = 35

        compilerOptions {
            jvmTarget.set(JvmTarget.JVM_17)
        }
    }

    sourceSets {
        commonMain.dependencies {
            implementation(libs.compose.runtime)
            implementation(libs.compose.foundation)
            implementation(libs.compose.ui)
        }
    }
}
#+end_src

**** Desktop Application

The =desktopApp= project is a JVM application that provides the desktop
entry point for Jetpacs.

It owns desktop process and window lifecycle, while application UI and
shared behavior remain in =:shared=.

The build runs on JDK 25 while emitted JVM bytecode remains compatible
with JVM 17.

#+begin_src kotlin :tangle desktopApp/build.gradle.kts :mkdirp yes
import org.gradle.api.JavaVersion
import org.gradle.api.tasks.compile.JavaCompile
import org.jetbrains.kotlin.gradle.dsl.JvmTarget

plugins {
    alias(libs.plugins.kotlinJvm)
    alias(libs.plugins.composeMultiplatform)
    alias(libs.plugins.composeCompiler)
}

kotlin {
    compilerOptions {
        jvmTarget.set(JvmTarget.JVM_17)
    }
}

java {
    sourceCompatibility = JavaVersion.VERSION_17
    targetCompatibility = JavaVersion.VERSION_17
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

dependencies {
    implementation(project(":shared"))
    implementation(compose.desktop.currentOs)
}

compose.desktop {
    application {
        mainClass = "jetpacs.desktop.MainKt"
    }
}
#+end_src

One subtlety: Kotlin's jvmTarget = 17 controls bytecode compatibility but does not by itself prevent Kotlin code from referencing JDK APIs newer than 17. Kotlin has a corresponding -Xjdk-release=17 capability for that purpose. Kotlin I would not add that raw compiler flag yet. A cleaner long-term solution, if we decide strict JDK-17 API enforcement is important, is a real Gradle Java 17 toolchain. Gradle and Kotlin both support separating that toolchain from the JDK 25 that runs Gradle. [fn:1]

***** Android Application

The =androidApp= project provides the Android application entry point.

It depends on =:shared= for shared Kotlin and Compose UI. Android
process, Activity, manifest, application identity, and lifecycle
configuration remain platform-specific.

AGP 9 provides built-in Kotlin support, so the legacy
=org.jetbrains.kotlin.android= plugin is intentionally not applied.

#+begin_src kotlin :tangle androidApp/build.gradle.kts :mkdirp yes
import org.gradle.api.JavaVersion
import org.jetbrains.kotlin.gradle.dsl.JvmTarget

plugins {
    alias(libs.plugins.androidApplication)
    alias(libs.plugins.composeMultiplatform)
    alias(libs.plugins.composeCompiler)
}

android {
    namespace = "dev.jetpacs"
    compileSdk = 37

    defaultConfig {

        targetSdk = 37

        versionCode = 1
        versionName = "0.1.0"
    }

    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17

        compose = true

****** Android Entry Point

The Android entry point is a =ComponentActivity=.

It owns Android lifecycle integration and installs the same shared
=:shared= Compose UI used by the desktop application.

#+begin_src kotlin :tangle androidApp/src/main/kotlin/dev/jetpacs/MainActivity.kt :mkdirp yes
package dev.jetpacs

import android.os.Bundle
import androidx.activity.ComponentActivity
import androidx.activity.compose.setContent
import jetpacs.App

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        setContent {
            App()
        }
    }
}
#+end_src

***** Known Toolchain Warnings

****** Android SDK XML Version

AGP 9.1.1 currently emits:

#+begin_example
Warning: SDK processing. This version only understands SDK XML versions
up to 3 but an SDK XML file of version 4 was encountered.
#+end_example

The Android target nevertheless compiles successfully, and AGP 9.1.1
officially supports Android API 37.0.

This warning is treated as a known Android tooling compatibility warning
rather than a build failure.

Revisit when upgrading AGP or if SDK processing begins to fail.
