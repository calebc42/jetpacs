| Setting      | Question it answers                                             |

| `minSdk`     | **How old may the device be?**                                  |

******* 10. Why not just set minSdk = 1?
Because backwards compatibility costs something.
Suppose an API was introduced in Android 12.
If your: =minSdk = Android 12= you can generally just use it.
If your minSdk = Android 7 you may need to do:
#+begin_example

    // new API
} else {
    // fallback implementation
}
#+end_example

AndroidX libraries and desugaring hide a lot of this complexity, but not all of it.
A lower minimum SDK therefore gives you:
More potential users
but also:
More compatibility states to test and support.
A higher minSdk gives you:
Simpler development
but:
Excludes older devices.

The colon explicitly means:

```text

└── root project

└── wrapper task belonging to root project
```

Gradle now recommends addressing the root Wrapper task explicitly this way. 

The other arguments mean:

```text
--gradle-version 9.5.0

    The Wrapper shall use exactly Gradle 9.5.0.


--distribution-type bin

    Download the smaller binary distribution,
    not sources/docs.


--gradle-distribution-sha256-sum 553c...

    When the Wrapper downloads Gradle 9.5.0,
    verify its bytes against this digest.
```

Gradle specifically supports `distributionSha256Sum` so Wrapper downloads can be cryptographically checked before use.

### 1. Teach Gradle where things come from

There are two separate repository systems in Gradle:

```text
Gradle plugins
    ↓
pluginManagement.repositories

application/library dependencies
    ↓
dependencyResolutionManagement.repositories
```

Gradle explicitly treats plugin repositories separately from project dependency repositories. Also, `pluginManagement {}` must be the first block in `settings.gradle.kts`. 

Replace your current `settings.gradle.kts` source block with:

```org
***** Dependency and Plugin Resolution

Gradle resolves build plugins separately from libraries used by the
application.

The =pluginManagement= block defines where Gradle searches for plugins
such as Kotlin, Compose Multiplatform, and the Android Gradle Plugin.

The =dependencyResolutionManagement= block defines where project
dependencies are resolved.

#+begin_src kotlin :tangle settings.gradle.kts
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)

    repositories {
        google()
        mavenCentral()
    }
}

#+end_src
```

The settings script is evaluated before project build scripts, which is why build-wide resolution policy belongs here. 

### Why `FAIL_ON_PROJECT_REPOS`?

Without it, a future module could quietly do this:

```kotlin
repositories {
    someRandomRepository()
}
```

and Gradle would start resolving dependencies from somewhere outside the repository policy we established in `settings.gradle.kts`.

With:

```kotlin
repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
```

we are saying:

> Dependency repositories belong to the build, not individual modules.

That is useful for reproducibility and auditing.
